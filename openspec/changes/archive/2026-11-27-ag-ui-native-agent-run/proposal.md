## Why

`Agent.run` emits a library-specific `Agent.Event` vocabulary that is, in practice, AG-UI with extra fields, and `AgUi.fold` (about 600 lines of span, step, subagent and replay bookkeeping) exists only to translate it back. The loop already follows AG-UI's run model (frontend calls, approval interrupts, steps, subagents), so keeping it "AG-UI agnostic" costs a second vocabulary and a projection stage that must reconstruct state the loop already had when it emitted. Separately, a request-scoped run should be a drop-in replacement for `effect/ai`'s `AgUiServer.agent`, which it nearly is today but not quite (no `usage`, no `AgUiServer.RunInput`, no 400 on a tool-name clash).

## What Changes

- **BREAKING** `Agent.run` emits AG-UI events (`AgUiSchema.Event`) directly, including its own run lifecycle (`RUN_STARTED` … `RUN_FINISHED` / `RUN_ERROR`), steps, text, reasoning, tool calls, tool results, `ACTIVITY_SNAPSHOT` progress, and subagent events tagged with `subagentRunId`. The wire sequence a client sees stays the same as today's `fold` output.
- **BREAKING** `Agent.Event` is removed, along with `AgUi.fold` and `AgUi.conflateProgress`. The loop builds AG-UI events where it already holds the state: per-step span bookkeeping moves into the model step, cancel closers into `cancelStep`, and `SUBAGENT_STARTED` / `SUBAGENT_FINISHED` into `callSubagent`, with no buffering of a child's finish until its parent's result.
- `Agent.run`'s element type is exactly `AgUiSchema.Event`, with no library-specific union member. Runner state that AG-UI can't carry leaves the stream:
  - **Entries.** A step's thread entries hold reasoning signatures, file parts, approval-request parts, frontend and subagent marks, and owner tags, so they can't be rebuilt from the events. The loop hands them to an internal step-finished hook (`OnStepFinished`, in `src/internal/`, not exported from the package) before it emits the step's `STEP_FINISHED`. A runner installs one that calls the history attempt's `commit`, and a parent run installs one per subagent. Applications never provide it: an eval asserts on AG-UI events, and one that checks what is stored runs through a runner with `History.layerServer` and reads the thread back with `History.restore`. A commit failure ends the run with `RUN_ERROR`.
  - **The failure cause.** Before it emits `RUN_ERROR`, the loop hands the original cause to a second internal hook, `OnRunFailed`. The runner logs it and ends the run's root span with it, with error status and `error.type` from `RUN_ERROR.code`, so an exporter records the original error once.
  - **The run's end.** The history's `end`, which releases the thread claim, stays in the runner and is triggered by the terminal AG-UI event. It reads the outcome type or `RUN_ERROR.code` from that event, so the claim is still released only after everything before the terminal event has been appended to the event log.

  Committing from the loop doesn't change the guarantees against the event log. The loop already runs ahead of its consumer through an unbounded buffer, so its model and tool checkpoints can already be stored before their events are logged. A commit is one more store write of that kind.
- A replayed event is emitted only when an earlier attempt may have checkpointed its work without publishing it: a replayed `TOOL_CALL_RESULT` or a subagent's closing event. Each one carries the marker `metadata["effect-agent-harness"] = { replayed: true }`, so the runner can decide whether to publish it. Runners remove the marker before any event leaves them. Every other replayed event is not emitted at all.
- A failed `TOOL_CALL_RESULT` carries `effect/ai`'s own marker, `metadata["effect/ai"] = { isFailure: true }`, which `AgUiServer.agent` emits and `AgUi.toPrompt` reads. `@ag-ui/client` copies event metadata onto the tool message it builds, so the marker round-trips: under the client history, a failed result sent back by the client stays failed. Today it comes back as a success, because only `History.restore`'s `error` field carried the failure. The client-history conversion and frontend-call answers read the marker as well as `error`, and `History.restore` adds the marker next to `error`.
- `RUN_FINISHED` reports `usage` summed over every model step, as `AgUiServer.agent` does.
- **BREAKING** `Agent.CurrentRun` and `RunInfo` are replaced by `effect/ai`'s `AgUiServer.RunInput`. `Agent.run` takes the run's AG-UI input itself (`{ input, prompt, subagentPrompts?, cancelled? }`) and provides it as `RunInput` to system prompts, approval predicates and tool handlers, a subagent's included. Its run id, thread id, `forwardedProps` (the old `props`) and `tools` (the old `frontendTools`) all come from that input. Tools written for `AgUiServer.agent` run unchanged, and tools can now read AG-UI `state`. The conversation still comes only from `prompt`: under the server history, `input.messages` is just what the client sent.
- **BREAKING** A run whose frontend tools reuse the name of one of the agent's tools or subagents no longer drops the frontend tool with a warning. `Agent.run` ends with `RUN_ERROR` code `FrontendToolConflict` without calling the model, and the `AgUiServer.Agent` surface rejects the input before its stream opens, which the AG-UI endpoint answers with 400.
- `Runner.toAgUiServerAgent(agent, options?)` adapts an agent to `effect/ai`'s `AgUiServer.Agent` interface, so it can be served with `AgUiServer.layerHttp({ agent })` / `agentHandler` like `AgUiServer.agent(...)`. It is an adapter over `makeAttached`, not a new runner: its runs are request-scoped runs. The only thing it adds is a 400 on a frontend tool clash. Because `agentHandler` captures its services when the route is built, apps with per-request services such as authentication keep using `endpoint` + `handler` with `makeAttached`.
- **BREAKING** Evals and tests read AG-UI events from `Agent.run` (for example, `RUN_FINISHED.outcome`) instead of `Agent.Event`s.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `agent-run`: the run takes its AG-UI input and provides it as `AgUiServer.RunInput` in place of the current run's info, and it produces AG-UI events instead of step events. This changes the "Run from a prompt to step events", "Step entries" (entries go to an internal step-finished hook before `STEP_FINISHED`) and "Replayed work is marked" (replays aren't emitted except for metadata-marked results and subagent terminals) requirements, along with the progress and cancellation wording.
- `agui-agent-loop`: failed tool results carry `effect/ai`'s failure marker, which is read back from client tool messages; the current run is the whole AG-UI input (`state` and `context` included, all untrusted), and the terminal event carries `usage`, summed over the run's model steps, its children's and replayed steps included. Tool progress is described without the intermediate tool-progress event.
- `agui-transport-edge`: an adapter makes a request-scoped runner usable as an `AgUiServer.Agent` (a tool-name clash is answered with 400), and runners never let the replay marker reach a client or the log.

`agui-subagent-events` describes wire behaviour only, which doesn't change. Only its Purpose line ("Projects child agent runs onto the AG-UI event stream") is reworded, directly in the main spec.
- `run-history`: under the client history, a `tool` message carrying `effect/ai`'s failure marker is a failed result.
- `thread-history-read`: a restored failed tool message carries the failure marker as well as `error`, matching the live stream.
- `agent-subagents`: a child sees its parent's AG-UI input, and a child's entries are committed with the parent step's entries, through the step-finished hook, instead of being carried by the parent's step-finished event.
- `agent-tracing`: a failed run's root span takes its error status and `error.type` from `RUN_ERROR`, and ends with the original error, which an exporter records as its one exception event. A subagent failure the parent handles ends the subagent's span with the child's error and isn't logged as an error.

## Impact

- **Code**: `Agent.ts` (emission, `callSubagent`, `cancelStep`, usage, calls to the step-finished hook, recording the failure on the span), `AgUi.ts` (removed: `fold`, `conflateProgress` and `handlePart` state move into or next to the loop, the builders (`approvalInterrupt` included) to `internal/events.ts`, `closeOpen` and `conflateActivity` to `internal/publish.ts`, and `ApprovalResponse` and `isTerminal` to `Agent`), `Runner.ts` (provides the step-finished hook from the attempt, a thin replay filter, `end` and `traced` driven by the terminal AG-UI event, plus the `AgUiServer.Agent` surface), `internal/history.ts` (`end` reads the AG-UI terminal event), `internal/conversions.ts` (reads the failure marker from client tool messages, and `restore` adds it).
- **Public API**: `Agent.Event`, `Agent.Outcome` (as an event payload), `AgUi.fold` and `AgUi.conflateProgress` are removed, the `AgUi` module is removed (its builders, `reasoningMessageId`, `closeOpen` and `conflateActivity` become internal, `AgUi.Event` gives way to `effect/ai`'s `AgUiSchema.Event`, and `ApprovalResponse` and `isTerminal` move to `Agent`), along with `Agent.CurrentRun`, `Agent.RunInfo` and `Agent.FrontendTool`. `Agent.run`'s input becomes `{ input, prompt, subagentPrompts?, cancelled? }`, and its element type becomes `AgUiSchema.Event`.
- **Tests**: nearly every test that reads `Agent.run` directly (`Agent`, `Subagents`, `Cancellation`, `VolatileSystem`, `Telemetry`, `AgUi`) is rewritten against AG-UI events, still passed through `verify`.
- **Docs**: `docs/robodocs.md` ("Testing and evals", the event table, the "Tool progress" migration note), `docs/architecture.md` (the map and run timeline lose the `fold` stage), and the library's `AGENTS.md`.
- **Dependencies**: none new. Effect's `AgUi.fromStreamParts` isn't reused, because it takes message ids from the provider, which isn't deterministic across a replay.
