# packages/examples/tanstack

A runnable example: a browser chat built with TanStack Start (SPA mode) and TanStack AI's `useChat`, talking to an effect-agent-harness agent backed by Anthropic.

TanStack AI speaks AG-UI in both directions: `fetchServerSentEvents` posts a `RunAgentInput` and reads AG-UI events back as `data:` SSE frames. effect-agent-harness's `Runner` and `Sse` already produce exactly that, so there is no translation layer.

- `src/server/chat.server.ts`: defines the agent with `Agent.define` (weather and email tools; the system prompt names today's date; one subagent, `weather-desk`, with the same tools), turns reasoning on in the model layer (`thinking` with `display: "summarized"`, without which the API returns thinking with no text), and builds the routes with `HttpRouter`, exposed as a web handler (`HttpRouter.toWebHandler`). `POST /api/chat` starts a detached run (`Runner.makeDetached`) and streams its `EventLog` back as SSE with `Sse.encodeStored`; a disconnect or a reload doesn't reach the run. `POST /api/chat/cancel` takes the `{ runId, threadId }` that TanStack AI's `stop()` posts to `cancelUrl`, calls `detached.cancel` and answers `204`: the run ends with `RUN_FINISHED` outcome `cancelled`, its partial reply is committed, and the thread is free. The frames carry cursors, so after a dropped connection TanStack re-sends the `POST` with `Last-Event-ID`: the route then only follows the log, because a second `start` would fork a second attempt of a run in flight. Event streams end after two minutes with no event (`IDLE_TIMEOUT`), because a crashed run's log never ends. `GET /api/chat?threadId=…&offset=-1&runId=…` is TanStack AI's join of a run, replayed from the start: `-1` is TanStack's marker and means no cursor, and `Last-Event-ID` wins when present. `GET /api/chat?threadId=…` is TanStack AI's server hydrate: it answers `{ messages, interrupts, activeRun }` from `History.restore(threadId, { rejoin: true })` over the stored thread, which leaves out what the join will replay, converting the AG-UI messages to `UIMessage`s (`toUIMessages`) with `@tanstack/ai`'s `convertMessagesToModelMessages`, which folds each `reasoning` message into the assistant message after it, and `modelMessagesToUIMessages`. A subagent's messages come back tagged with its `subagentRunId`; `toUIMessagesWithSubagents` converts each subagent's messages the same way (untagged, or TanStack's converter would split them off again) and puts them in a `subagent` part on the message holding the spawning call, as TanStack builds them from a live run. The card's name and spawning call come from the call (`Agent.subagentIdFor(call.id)` is the child's id), its description from the subagent's definition, and its status from the call: `error` (with the message) when the result is a failure, which `restore` marks with `error`, as live `SUBAGENT_ERROR` did; `finished` with any other result; otherwise `suspended`, with the open interrupts the child owns. A child that failed before writing any message has no card, as live. The hydrate isn't AG-UI: TanStack requires `UIMessage`s there. A step that produced only reasoning isn't shown after a reload. The server owns the transcript: the stores layer provides `History.layerServer` over `Thread.layerMemory`, keeping `Thread` in its output for the hydrate route, which a client history couldn't serve. The stores layer also provides `Checkpoint.layerNone` and `EventLog.layerMemory`. The `.server.ts` suffix keeps it out of the client bundle.
- `src/routes/api/chat.ts`: a Start server route that forwards `GET` and `POST` to that handler. `src/routes/api/chat_.cancel.ts` forwards `POST /api/chat/cancel` to it too (the `_` keeps it from being a child of `/api/chat`).
- `src/routes/index.tsx`: the chat UI. The thread id is the `?thread=` search param; a page without one generates one and replaces the URL, so a reload continues the thread and a new tab starts a new one. `useChat` runs with `persistence: true`, so on mount it restores the thread's messages and open approvals from the hydrate and rejoins a run still going. The connection URL carries the thread id, because TanStack's join request doesn't add it and the event log is keyed by thread. The connection sets `cancelUrl: "/api/chat/cancel"`, so `useChat`'s `stop()` also cancels the run on the server (aborting the stream alone wouldn't reach a detached run). While a run streams, the page shows Stop instead of Send, because the thread is busy until the run ends. TanStack AI treats a `cancelled` `RUN_FINISHED` like a finish, not an error, so the partial reply stays on screen. Known limitation: rejoining a continuation (a run answering an approval, with no new user message) loses the earlier assistant message from view until the next reload after the run ends, because TanStack drops the last hydrated assistant message when a replay starts and that run's log doesn't rebuild it. Never set its `history.pageSize`: with paging, the client posts only the messages it hasn't loaded, which the server rejects with `HistoryMismatch`.
  - **Approvals:** effect-agent-harness's approval interrupts are plain AG-UI interrupts, without the binding metadata TanStack AI puts on its own, so `useChat` lists them in `interrupts` as `kind: "unbound"` with no `resolveInterrupt`. The page renders its own Approve/Deny card per interrupt and, once every pending approval has a decision, answers with `resumeInterruptsUnsafe`: one `{ interruptId, status: "resolved", payload: { approved } }` entry each (`AgUi.ApprovalResponse`). Input is disabled meanwhile, because the server rejects a run that leaves an approval unanswered.
  - **Subagents:** TanStack AI turns `SUBAGENT_STARTED` into a `subagent` part on the current assistant message and builds the child's own messages inside it from the events tagged with its `subagentRunId`. The page renders the part as a card (name and status) holding the child's messages, rendered like the assistant's. It needs no `subagents` option on `useChat`. A child's approval is an ordinary interrupt in `interrupts`, so the same Approve/Deny card answers it.
- `src/routes/__root.tsx`, `src/router.tsx`: the Start shell and router. `src/routeTree.gen.ts` is generated by the Start plugin when the dev server or a build runs; it is committed so `pnpm tsc` works without one, and is excluded from oxlint and oxfmt.
- `src/tools/weather.tool.ts`: the same Open-Meteo tool as the `ag-ui` example, with `failureMode: "return"`.
- `src/tools/email.tool.ts`: a `send-email` tool with `needsApproval: true`. It only prints to the dev server's console; nothing is sent.
- `src/tools/browser-time.tool.ts`: `get-browser-time`, a frontend tool (TanStack's `toolDefinition(...).client(...)`, its input an Effect schema through `Schema.toStandardJSONSchemaV1`). The page passes it to `useChat`'s `tools`, so every run advertises it in `RunAgentInput.tools` and effect-agent-harness offers it to the model next to the server's tools. A call to it ends the run with `RUN_FINISHED` `success` and `pendingToolCallIds`. The browser runs it as soon as the call streams, and TanStack starts the next run with its result as a `tool` message. The server needs no code for it. It's imported only by the page, so it stays out of the server.

Run it with `pnpm --filter tanstack dev` and open http://localhost:3000. It needs `ANTHROPIC_API_KEY` in the repo-root `.env`, which is gitignored. Never print, log or commit its value.

## Manual checks

This package has no tests; `pnpm tsc` and `pnpm lint` are its checks. After changing the runner, the SSE encoding or the thread handling, also run the example in a browser and check:

1. **Tool call:** ask "What's the weather in Paris?". A `get-weather {"location":"Paris"}` call appears; expanding it shows the tool's JSON result, and the assistant answers from it.
2. **Server-owned history:** then ask "Which city did I just ask about?". The answer must name Paris.
3. **Approval, approved:** ask "Email ada@example.com saying hello". The run stops with an "Approve call to send-email?" card and the input disabled. Approve: the dev server prints `📧 (not really) sending "..." to ada@example.com`, the tool call's result is `{"sent":true}`, the assistant confirms, and the input is enabled again.
4. **Approval, denied:** in the same conversation, ask for another email and deny it. Nothing prints, the result is `{"type":"execution-denied","reason":"denied"}`, and the assistant says it could not send.
5. **Reload keeps the thread:** reload the page. The URL keeps its `?thread=`, and the conversation so far reappears, tool calls and their results included.
6. **Follow-up after reload:** ask "Which city did I ask about first?". The answer must name Paris, and the run must not fail with `HistoryMismatch` or `HistoryDiverged`.
7. **Approval survives a reload:** ask for another email, and reload while the approval card is showing. The card comes back with the input disabled. Approve it: the dev server prints the email, and the assistant confirms.
8. **New tab:** open http://localhost:3000 in a new tab. It gets a new `?thread=` and an empty conversation.
9. **Frontend tool:** ask "What time is it where I am?". A `get-browser-time` call appears, and its result (your browser's time and time zone) appears without a server log line. A second run follows on its own, and the assistant answers from the result. The dev server shows no `UnansweredToolCall`.
10. **Mixed step:** in a new tab, ask "What's the weather in Paris, what time is it here, and email ada@example.com both". The run stops with the approval card. The browser time result is already shown, but no second run starts while the card is up. Approve: the dev server prints the email, and the assistant answers using the weather, the time and the sent email. Nothing fails with `UnansweredInterrupt` or `UnansweredToolCall`.
11. **Reasoning:** ask "Six people sit around a round table. How many seatings are there up to rotation? Reason carefully." One assistant message holds a collapsed "Reasoning" row above its reply, live and after a reload. A further turn after the reload runs without a history error.

12. **Subagent:** ask "Ask the weather desk for a report comparing Paris and Rome." A `weather-desk` tool call appears with a "🤖 weather-desk" card under it that fills in live: its own `get-weather` calls and its report. The card ends "done", and the assistant answers from the report.
13. **Subagent after reload:** reload. The card comes back closed, "done", with the desk's calls and report inside it, and a follow-up question runs without `HistoryMismatch` or `HistoryDiverged`.
14. **Approval inside a subagent:** ask "Have the weather desk email ada@example.com a report on Paris." The desk's card shows "waiting for approval" with its `send-email` call, and the Approve/Deny card appears. Reload: both come back. Approve: the dev server prints the email, the card continues under the same desk (no second card) and ends "done", and the assistant confirms.
15. **Stop:** ask "Write a 600-word story about a lighthouse keeper." and press Stop while it streams. The reply stops where it was, with no error, and Send comes back. Reload: the partial reply is still there. Ask "What was the keeper's name?": the run succeeds, with no `ThreadBusy`, `HistoryMismatch` or `HistoryDiverged`, and the answer comes from the partial reply.

This package exists to show how to use the library, so keep it idiomatic and minimal. Changes to library behaviour belong in `packages/effect-agent-harness`, with tests there.
