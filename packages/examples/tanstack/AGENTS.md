# packages/examples/tanstack

A runnable example: a browser chat built with TanStack Start (SPA mode) and TanStack AI's `useChat`, talking to an effentic agent backed by Anthropic.

TanStack AI speaks AG-UI in both directions: `fetchServerSentEvents` posts a `RunAgentInput` and reads AG-UI events back as `data:` SSE frames. effentic's `Runner` and `Sse` already produce exactly that, so there is no translation layer.

- `src/server/chat.server.ts`: defines the agent with `Agent.define` (weather and email tools; the system prompt names today's date), and builds the one route with `HttpRouter`, exposed as a web handler (`HttpRouter.toWebHandler`). `POST /api/chat` runs a request-scoped run (`Runner.make`) and streams it back as SSE; a disconnect (the client's `stop()`) cancels the run. Stateless: `Thread.layerMemory`, `Checkpoint.layerNone`, `EventLog.layerMemory`. The `.server.ts` suffix keeps it out of the client bundle.
- `src/routes/api/chat.ts`: a Start server route that forwards the request to that handler.
- `src/routes/index.tsx`: the chat UI. Each page load uses a fresh `threadId`, because the server owns the thread's history and rejects a client that reuses a stored thread id without it (`HistoryMismatch`).
  - **Approvals:** effentic's approval interrupts are plain AG-UI interrupts, without the binding metadata TanStack AI puts on its own, so `useChat` lists them in `interrupts` as `kind: "unbound"` with no `resolveInterrupt`. The page renders its own Approve/Deny card per interrupt and, once every pending approval has a decision, answers with `resumeInterruptsUnsafe`: one `{ interruptId, status: "resolved", payload: { approved } }` entry each (`AgUi.ApprovalResponse`). Input is disabled meanwhile, because the server rejects a run that leaves an approval unanswered.
- `src/routes/__root.tsx`, `src/router.tsx`: the Start shell and router. `src/routeTree.gen.ts` is generated by the Start plugin when the dev server or a build runs; it is committed so `pnpm tsc` works without one, and is excluded from oxlint and oxfmt.
- `src/tools/weather.tool.ts`: the same Open-Meteo tool as the `ag-ui` example, with `failureMode: "return"`.
- `src/tools/email.tool.ts`: a `send-email` tool with `needsApproval: true`. It only prints to the dev server's console; nothing is sent.

Run it with `pnpm --filter tanstack dev` and open http://localhost:3000. It needs `ANTHROPIC_API_KEY` in the repo-root `.env`, which is gitignored. Never print, log or commit its value.

## Manual checks

This package has no tests; `pnpm tsc` and `pnpm lint` are its checks. After changing the runner, the SSE encoding or the thread handling, also run the example in a browser and check:

1. **Tool call:** ask "What's the weather in Paris?". A `get-weather {"location":"Paris"}` call appears; expanding it shows the tool's JSON result, and the assistant answers from it.
2. **Server-owned history:** then ask "Which city did I just ask about?". The answer must name Paris.
3. **Approval, approved:** ask "Email ada@example.com saying hello". The run stops with an "Approve call to send-email?" card and the input disabled. Approve: the dev server prints `📧 (not really) sending "..." to ada@example.com`, the tool call's result is `{"sent":true}`, the assistant confirms, and the input is enabled again.
4. **Approval, denied:** in the same conversation, ask for another email and deny it. Nothing prints, the result is `{"type":"execution-denied","reason":"denied"}`, and the assistant says it could not send.
5. **Fresh page:** reload and ask again. It must work (a new thread), not fail with a history mismatch.

This package exists to show how to use the library, so keep it idiomatic and minimal. Changes to library behaviour belong in `packages/effentic`, with tests there.
