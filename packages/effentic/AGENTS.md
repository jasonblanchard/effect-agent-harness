# packages/effentic

The library. The public API is `src/index.ts`, which re-exports each module as a namespace (`AgUi`, `AgUiSchema`, `Messages`, `Agent`, `Sse`, `Thread`, `History`, `Checkpoint`, `EventLog`, `Runner`). Its only runtime dependency is `effect`. Consumers import from `"effentic"`, which resolves straight to the `.ts` sources (there's no build step).

## Modules

- `AgUi.ts`: Schemas for the subset of AG-UI `RunAgentInput` the agent reads (including `resume` entries, the advertised frontend `tools` as `FrontendTool`s with unchecked `parameters`, and the `ApprovalResponse` payload, whose JSON Schema every approval interrupt carries as `responseSchema`), the `Event` union it emits, and `fold`, which projects `Agent.Event`s onto AG-UI (step events, span bookkeeping including reasoning, the success outcome with `pendingToolCallIds` when frontend calls are pending, the approval `interrupt` outcome, which never carries them, closers before `RUN_ERROR`; replayed events are dropped). `approvalInterrupt` builds the approval interrupt for both `fold` and `History.restore`, so a reloaded client sees the interrupt the stream carried. Each reasoning block with text is one span holding one reasoning message, both under `reasoningMessageId(stepMessageId, n)`, with `n` counting every block of the step, with or without text; the id is derived rather than minted so that nothing new is stored, and it is exported for `restore` only (`@internal`; treat the format as opaque). `fold` opens a block lazily on its first text, reads only its text, and ignores a delta with no start, because `fromResponseParts` does: what it shows must be what `restore` can return. `closeOpen` computes the closers for spans an aborted attempt left open in a log, tracking reasoning messages and spans separately, because a log can stop between a block's two starts. Decoding is deliberately lenient: unknown fields are stripped, and unknown message roles pass through so later code can ignore them.
- `AgUiSchema.ts`: **generated, don't edit.** Effect schemas and types for the whole AG-UI 1.0 protocol (every event, message, `RunAgentInput`, capabilities, JSON Patch) plus `PROTOCOL_VERSION`, generated from the pinned `schema/ag-ui-1.0.json` (a copy of https://docs.ag-ui.com/spec/1.0/schema.json) by `scripts/generate-schema.ts` with Effect's own JSON Schema importer. Regenerate with `pnpm --filter effentic generate:schema`; to move to a new spec version, replace the pinned file first. The script's header lists how it rewrites the spec into what the importer accepts (flattened `allOf`, `unevaluatedProperties` as `additionalProperties`, `not null` dropped, `Schema.Finite` for numbers). The other modules take their AG-UI types from here; `AgUi.RunAgentInput` stays its own lenient subset on purpose. Event `type`s are plain string literals (`"RUN_STARTED"`), not an enum.
- `Messages.ts`: `Entry`, one message of a conversation as a run holds it (both histories produce entries, `Agent.run` emits them per step, and only the server history stores them in `Thread`), and `project`, which builds the model prompt from the entries verbatim (no system prompt: the agent adds it), with tool results moved next to their calls and unanswered calls given a failed result, except calls with an approval request, which the run resolves. Nothing else: the conversions the histories run are in `src/internal/conversions.ts`.
- `internal/conversions.ts`: the private half of `Messages`, not exported from the package: the pure conversions the two histories run, their helpers, and the server history's four errors (re-exported by `History`). `fromHistory` is the client history's conversion: the client's messages as entries under their own ids, with no reconciliation (user text; `system`/`developer` per `clientSystem`; assistant text and tool calls with parsed arguments, a call whose arguments aren't a JSON object dropped with its results (`droppedCalls`); a `tool` message as its call's result, decoded as `answers` decodes it, first per call, one with no call in the history dropped (`orphanResults`); other roles dropped), and `resume` resolved by working forward from the calls: an unanswered call whose `Agent.approvalIdFor` matches a resume entry gets the approval request part and a `<approvalId>:response` entry, built by the same private `decision` as `resume`. The rest serves the server history, where the client only contributes a delta: `delta` is the client messages after the last known one: a client message is known if its id is stored, or if it is a `tool` message whose `toolCallId` has a stored result (TanStack AI sends tool results under its own ids); unknown client messages are ignored. `HistoryMismatch` if the store is non-empty and nothing is known; `HistoryDiverged` if a stored entry after the last known one is one `restore` would show and no client message matches it, skipping entries the reconciled run committed itself (a run executed again after a crash). `restore` reads a thread back as the AG-UI messages its events showed, typed as AG-UI's `Message` (same ids and content, results after their calls, an entry's reasoning directly before its assistant message; system entries and approval responses hidden) plus its open approval interrupts and the run that raised them; it is public as `History.restore(threadId)`, which loads the thread from `Thread` first, and callers serve that from their own route. Its visibility rule (`shown`) is the one `delta` uses, so keep them together. Reasoning stays outside `shown`, in `reasoningOf`: an entry holding only reasoning would otherwise have to be matched, and a client's reasoning rows carry their blocks' ids, not the entry's. `ingest` keeps user text and, only with `clientSystem: "allow"`, system/developer messages; assistant and tool turns from the client are dropped. `answers` takes the client's `tool` messages for the frontend calls in the store that have no result yet (calls `Agent.isFrontendCall` recognises), the first per call, as tool-result entries under the client's ids (`error` → failed; JSON text parsed; parts reduced to text, others dropped and named in `droppedParts`, which the runner logs); a pending call without one is `UnansweredToolCall`, which the runner reports after `UnansweredInterrupt` and before committing anything. `restore` also returns `pendingToolCalls` (`runId`, `toolCallIds`). `resume` turns AG-UI `resume` entries into approval responses (approved only for `resolved` with an `AgUi.ApprovalResponse` payload whose `approved` is `true`; `malformedAnswers` names the `resolved` answers whose payload doesn't decode, and the runner logs them as a warning; a pending request without a resume entry is `UnansweredInterrupt`, which the runner reports before committing anything).
- `Agent.ts`: the core loop, independent of AG-UI. An approval's id is `approvalIdFor(toolCallId)` (`approval:<toolCallId>`), so a client's history alone links an interrupt to its call; treat the format as opaque. `define` turns a toolkit, system prompt and step limit into a plain `Agent<Tools, R>` value that names no provider or store, so the same value runs in production and in an eval. `system` is text or an `Effect<string, never, R>`, resolved once per run before step 0 and memoised as `system`; `R` joins `Requirements`. `run(agent)({ runId, threadId, props?, prompt })` provides that `RunInfo` as `CurrentRun` for the whole run (system effect, tool handlers whose tool declares `dependencies: [Agent.CurrentRun]`, approval predicates), excludes `CurrentRun` from `Requirements`, puts the system prompt first in every model call, and emits `Agent.Event`s: per model step `StepStarted`, live `ModelPart`s, then `ToolResult` / `ApprovalRequested` and `StepFinished` (carrying the step's thread entries), ending with one `Finished` or `Failed`. The model is called with `disableToolCallResolution`; the loop runs each tool call itself after the model step. Every model call (`model:<step>`) and tool call (`tool:<toolCallId>`) goes through `Checkpoint.memo`, and every id is minted inside its checkpoint, so a run executed again with the same `runId` replays completed steps (marked `replayed: true`, with no `ModelPart`s) and never re-runs a tool handler. Approval responses already in the prompt are resolved first as step 0. `RunInput.frontendTools` (not part of `RunInfo`) become `Tool.dynamic`s offered next to the toolkit's tools, in a `WithHandler` built per run whose `handle` is the toolkit's; a frontend tool named like a server tool is dropped with a warning. A frontend call in a step that finishes `tool-calls`/`stop` runs nothing and isn't checkpointed (the memoised model step and input make it deterministic): its tool-call part in the step's assistant entry gets `options.effentic.frontend`, the run stops after the step, and both outcomes list it in `pendingToolCalls`. `forModel` removes that mark, and approval parts, before every model call.
- `History.ts`: who owns a run's transcript. `History` is an optional service with an opaque type, read from the run's context (`Effect.serviceOption`); a run without one uses the client history. `layerClient` (the default; provide it to force the client history inside a context holding a server one) takes `input.messages` as the run's history via the internal `fromHistory` and stores, claims and releases nothing. `layerServer` (requires `Thread`) is the server-authoritative behaviour: claim, load, `delta`/`resume`/`answers`/`ingest`, commit, per-step commits, `runEnded` then `release` before the terminal event. It also exports the server history's rejections (`HistoryMismatch`, `HistoryDiverged`, `UnansweredInterrupt`, `UnansweredToolCall`, defined in `internal/conversions.ts` and re-exported, so their tags and `RUN_ERROR` codes are the same) and `restore(threadId)`, an `Effect<Restored, ThreadError, Thread>` that loads the thread and converts it with the internal `restore`, with no claim and no `History` service. The module comment holds the security model. The implementations live in `src/internal/history.ts`, which the package doesn't export: a private `Service` (`beginAttempt(input, { clientSystem })` returning an `Attempt` of `stored`, `added`, `commit`, `end`; and `abandonAttempt(input)`, which `run` calls when its stream stops before a terminal event, whether or not `beginAttempt` returned). `beginAttempt` runs again on every attempt, so implementations must be idempotent; the server's `beginAttempt` reports a failure after its claim (`runEnded`, `release`) before failing, as `end` would.
- `Thread.ts`: the server history's thread store, read only through `History.layerServer` (`load`, `claim`/`release` for the one active run, idempotent per-step `commit` of `Messages.Entry`s, `runEnded`) and `layerMemory`. `load` returns each entry with the `runId` of the commit that appended it (`History.restore` and `delta` rely on it). Compaction is the store's concern: the prompt is built from whatever `load` returns, but `delta` and `resume` read it too, so a compacted thread must keep the client's latest ids, any unanswered approval requests and any pending frontend calls (with their tool-call `options`), and must not add a non-system entry after the latest one the client has seen (`HistoryDiverged`).
- `Checkpoint.ts`: memoises named steps of a run (`memo`), keyed by `(threadId, runId, name)`. `layerNone` (tests, evals), `layerLedger` over a caller-supplied `Ledger` (`layerMemoryLedger` for tests), `layerWorkflow` (activities; build it inside a workflow execution). Completed exits, including failures, are stored; interrupted attempts are not.
- `EventLog.ts`: a run's AG-UI events under increasing cursors, keyed by `(threadId, runId)`; `subscribe` checks the cursor first (an unissued one fails with `InvalidCursor` before any stream exists, so routes can answer 400), then yields history then live events and completes after the terminal event, at once if the cursor is already past it. `read` rejects unissued cursors too. `layerMemory`.
- `Runner.ts`: the AG-UI edge. All runners share one pipeline with no branch on the history: build `Options.layer` from the dependencies the run was provided, in the attempt stream's scope (not memoised: every attempt and replay builds it again); check the input against the run's memoised `input` (`RunInputMismatch` if it differs; the dependencies aren't part of it); open the run's `History` (`beginAttempt`; under `layerServer` that claims, loads, reconciles and commits, failing with `ThreadBusy`, `HistoryMismatch` and so on); project `stored ++ added` (memoised as `prompt`); run the agent with `RunInfo` (`props` from `forwardedProps`), the input's `tools` as `frontendTools` and the per-run services provided, handing each `StepFinished` to `attempt.commit`; hand the terminal event to `attempt.end` (after the failure catch, and before the event is emitted, so the server history reports and releases first); then `AgUi.fold`. `run` abandons a run whose stream stops before its terminal event (a cancelled request; the server history releases its claim); detached and workflow runs keep the claim until they are resumed and end. Where each runner reads its history: `run` from the stream's context (so it can vary per request); `makeDetached` from the captured context, overridden by one provided around `start`; `workflow` from the context its `layer` is built in (a payload can't hold a service, so it can't vary per run). Choose a runner by whether a disconnect should cancel the run:
  - `run` is request-scoped: the consumer stopping cancels the run. It's a plain function and captures nothing. A route calls it in its handler, provides the per-request service, and closes over the handler's context (`Effect.context` + `Stream.provideContext`) before handing the stream to the response, since the body is read after the handler has returned (the examples' `sse` helper). With `effect/http` the handler's services must be in the app layer's output (`Layer.provideMerge`), which `toWebHandler`/`serve` provide per request; `Layer.provide` hides them, and the web handler then demands a context argument.
  - `makeDetached` forks the run into a caller-owned scope and writes it to the `EventLog`; disconnects don't reach it. Starting the same input again completes a crashed attempt: nothing happens if the log is terminal, otherwise open spans are closed, `RUN_STARTED` isn't repeated, and replayed steps publish nothing.
  - `workflow` is the detached body as an `effect/workflow` workflow named by the required `WorkflowOptions.name` (unique per agent on an engine; it is persisted, so never default or rename it) and keyed by the input's thread id and run id, with `Checkpoint.layerWorkflow`. Its dependencies must be `RunContext`s; its payload schema is built per workflow from them (`{ input, context }` keyed by each one's key, or `{ input }` with none), so a resumed execution has its dependencies and the engine validates them on encode. `start(input)` reads the dependencies from the caller, builds the payload and executes with `discard`; `executionId(input)` needs them too, because the engine derives the id from the encoded payload.
  - `Options.layer` builds per-run services on every runner. `DetachedOptions.dependencies` (`makeDetached`, `workflow`) lists services each run requires from its caller (any service key, like a tool's `dependencies`; `RunContext`s for `workflow`), because those runners capture their services when built and must leave these out; `run` has no `dependencies`, since it captures nothing. `RunContext<Self>()(key, { schema })` is a `Context.Service` class plus its `schema` (not `context`, which clashes with `Context.Service`'s own method). Runners take only the input: `run` leaves every service on its stream, and `makeDetached`'s `start` leaves the dependencies (`DependencyServices<Dependencies>`), reading them before forking. `Requirements` (what a detached or workflow runner captures; a `run` stream requires it with no dependencies) is the agent's requirements minus what the layer provides and the dependencies, plus the layer's own needs, plus `Checkpoint` (used before the services exist). Not `Thread`: the history is optional, and `History.layerServer` brings its own store. Read a dependency's service type from its key's `Identifier`, not `InstanceType`, which is `any` for these classes.
- `Sse.ts`: encodes AG-UI events as SSE frames, the format `@ag-ui/client`'s `HttpAgent` expects. `encodeStored` sets each frame's SSE `id` to the event's cursor, for `Last-Event-ID` reconnects. `response` is the `effect/http` response for those frames: it closes over the context it's built in (the body is read after the handler returns), and sets `text/event-stream` and `cache-control: no-cache`, with the caller's `headers` merged over them. It's the module's only `effect/http` import; the encoders stay transport-free.

## Resume rules

- **Approvals.** A tool with `needsApproval` ends the run with `RUN_FINISHED` outcome `interrupt` (one interrupt per approval, `reason: "tool-approval"`, id `Agent.approvalIdFor(toolCallId)`). The next run on the thread answers with `resume` entries; approved calls execute as step 0 before the model is called. Under the server history, the entries are matched against the stored requests, and a run that leaves an open approval unanswered fails with `UnansweredInterrupt` (AG-UI 1.0 forbids reading an omission as a decision); the client gives up on one by answering `cancelled`. Under the client history, an entry answers the unanswered call in the client's history whose derived id it names, and an entry naming nothing is ignored; the run can't know what the previous run left open, so a call left unanswered is sent to the model with a failed result instead of failing the run. A client that drops a call's result and approves it again runs the handler again: the security model accepts that (see `History.ts`).
- **Frontend tools.** A call to a tool the client advertised ends the run with `RUN_FINISHED` `success` and `pendingToolCallIds` (or with the approval interrupt, if the step also requested one). The next run answers each call with a `tool` message in `messages`. Under the server history, one that leaves a call out fails with `UnansweredToolCall`, and a mixed step needs both its `resume` entries and its tool messages before step 0 runs the approved calls. Under the client history, a result is a `tool` message like any other, and an unanswered call gets a failed result.
- **Run context.** A detached run doesn't store its dependencies: restarting one means calling `start` with the same input and the same dependencies provided, and builds the per-run services again. A computed system prompt is memoised as `system`, so a resumed run sends the first attempt's text even if the services it read changed.
- **Crashes.** Re-running a `runId` with a durable `Checkpoint` replays completed model and tool steps (same ids, no repeated handlers) and re-executes only the step that was in flight, with fresh ids. A step that _failed_ is memoised too: a failed run stays failed, and the client retries with a new `runId`.

## Invariants

- **One active run per thread, under the server history.** `History.layerServer` claims the thread before loading it and releases it before the terminal event. Never load or commit outside a claim, and never emit `RUN_FINISHED`/`RUN_ERROR` for a claimed run before releasing it, or a client's immediate next run gets `ThreadBusy`.
- **Every key for a run includes the thread id.** The client picks `runId`, so checkpoints, the workflow idempotency key and the event log are keyed by `(threadId, runId)`. The caller authorises the thread, and that must be enough to authorise its runs.
- **Per-run dependencies never come from the AG-UI input.** Only the runner's caller provides them (the verified principal, not the token), and they reach the agent only as services; the client's `forwardedProps` only ever becomes `props`, which is untrusted. A per-run layer failure happens before the history is opened, so it isn't reported through `runEnded`.
- **The event streams never fail.** `Agent.run` reports errors (model failures, `StepLimitExceeded`, …) as one in-band `Failed` event, and the AG-UI streams as `RUN_ERROR`; the error type is `never`. Keep it that way.
- **Every emitted sequence must be valid AG-UI.** That means a run lifecycle (`RUN_STARTED` … `RUN_FINISHED`/`RUN_ERROR`), and text messages, reasoning messages and spans, tool calls and steps that are started, then ended, never left open. This includes an event log completed by a resumed attempt.
- **A client writes only the results of its own calls, under the server history.** (Under the client history the client owns the transcript and writes what it likes; tool handlers and per-run services are the authorization boundary.) A client `tool` message is committed only as the result of a stored call marked as a frontend call that has no result yet (`answers` in `internal/conversions.ts`); `ingest` drops every other one. Never derive a frontend call from its tool name: the conversions don't see the toolkit, and a server call left open by a crash must not become answerable.
- **Side effects go through checkpoints.** Every model call, tool call and id minted in a run happens inside one `Checkpoint.memo`, so a replay is deterministic and handlers run at most once per run.
- New tools should normally use `failureMode: "return"`, so their failures go back to the model instead of ending the run.

## Tests

- Use `@effect/vitest` (`it.effect`) for anything effectful.
- `test/fixtures.ts` provides a `scriptedModel(steps)` fake `LanguageModel`. Each step is the stream for one `streamText` call, and it records the prompts it receives. It also provides part builders (`text`, `reasoning`, `toolCall`, `finish`, plus `signature` for a block's metadata and `wholeReasoning`, which isn't a stream part, so it goes straight to `AgUi.fold`), a sample `WeatherToolkit` with `countingWeatherLayer()`, an `ApprovalToolkit` (adds `send-email`, which needs approval) with `countingApprovalLayer()`, frontend tool definitions (`PickFile`, `GetLocation`) and `toolAnswer` (a client tool message under a TanStack-style id), the tools each model call was offered (`scriptedModel(...).tools`), `evalLayers` (`Checkpoint.layerNone` + `counterIds`), `serverStores` (`History.layerServer` over `Thread.layerMemory`, keeping `Thread` in the output) and `serverHistory(threadLayer)` for stubs, `runAgUi` (several inputs through `Runner.run`; client history unless a history is provided around it), deterministic ids (`counterIds`) and `verify`.
- To test a crash, stop consuming the run mid-step (or close a detached run's scope) and run the same `runId` again against a shared `Checkpoint.layerMemoryLedger`.
- **Pass every event sequence a test produces through `verify`.** It decodes each event against `AgUiSchema.Event` (undeclared fields rejected) and runs `@ag-ui/client`'s own sequence checks, so the tests catch events the spec doesn't allow and streams a real client would reject. `@ag-ui/client` is a dev dependency only.
- Don't call a real model in tests.
