# packages/effentic

The library. The public API is `src/index.ts`, which re-exports each module as a namespace (`AgUi`, `Messages`, `Agent`, `Sse`, `Thread`, `Checkpoint`, `EventLog`, `Runner`). Consumers import from `"effentic"`, which resolves straight to the `.ts` sources (there's no build step).

## Modules

- `AgUi.ts`: Schemas for the subset of AG-UI `RunAgentInput` the agent reads (including `resume` entries and the `ApprovalResponse` payload, whose JSON Schema every approval interrupt carries as `responseSchema`), the `Event` union it emits, and `fold`, which projects `Agent.Event`s onto AG-UI (step events, span bookkeeping, the approval `interrupt` outcome, closers before `RUN_ERROR`; replayed events are dropped). `approvalInterrupt` builds the approval interrupt for both `fold` and `Messages.history`, so a reloaded client sees the interrupt the stream carried. `closeOpen` computes the closers for spans an aborted attempt left open in a log. Decoding is deliberately lenient: unknown fields are stripped, and unknown message roles pass through so later code can ignore them.
- `Messages.ts`: pure functions between AG-UI messages and `Thread.Entry`s. The server owns the history, so the client only contributes a delta: `delta` is the client messages after the last known one: a client message is known if its id is stored, or if it is a `tool` message whose `toolCallId` has a stored result (TanStack AI sends tool results under its own ids); unknown client messages are ignored. `HistoryMismatch` if the store is non-empty and nothing is known; `HistoryDiverged` if a stored entry after the last known one is one `history` would show and no client message matches it, skipping entries the reconciled run committed itself (a run executed again after a crash). `history` reads a thread back as the AG-UI messages its events showed (same ids and content, results after their calls; system entries, approval responses and reasoning hidden) plus its open approval interrupts and the run that raised them; callers serve it from their own route. Its visibility rule (`shown`) is the one `delta` uses, so keep them together. `ingest` keeps user text and, only with `clientSystem: "allow"`, system/developer messages; assistant and tool turns from the client are dropped. `resume` turns AG-UI `resume` entries into approval responses (approved only for `resolved` with an `AgUi.ApprovalResponse` payload whose `approved` is `true`; `malformedAnswers` names the `resolved` answers whose payload doesn't decode, and the runner logs them as a warning; a pending request without a resume entry is `UnansweredInterrupt`, which the runner reports before committing anything). `project` builds the prompt from the entries verbatim (no system prompt: the agent adds it), with tool results moved next to their calls and unanswered calls given a failed result, except calls with an approval request, which the run resolves.
- `Agent.ts`: the core loop, independent of AG-UI. `define` turns a toolkit, system prompt and step limit into a plain `Agent<Tools, R>` value that names no provider or store, so the same value runs in production and in an eval. `system` is text or an `Effect<string, never, R>`, resolved once per run before step 0 and memoised as `system`; `R` joins `Requirements`. `run(agent)({ runId, threadId, props?, prompt })` provides that `RunInfo` as `CurrentRun` for the whole run (system effect, tool handlers whose tool declares `dependencies: [Agent.CurrentRun]`, approval predicates), excludes `CurrentRun` from `Requirements`, puts the system prompt first in every model call, and emits `Agent.Event`s: per model step `StepStarted`, live `ModelPart`s, then `ToolResult` / `ApprovalRequested` and `StepFinished` (carrying the step's thread entries), ending with one `Finished` or `Failed`. The model is called with `disableToolCallResolution`; the loop runs each tool call itself after the model step. Every model call (`model:<step>`) and tool call (`tool:<toolCallId>`) goes through `Checkpoint.memo`, and every id is minted inside its checkpoint, so a run executed again with the same `runId` replays completed steps (marked `replayed: true`, with no `ModelPart`s) and never re-runs a tool handler. Approval responses already in the prompt are resolved first as step 0.
- `Thread.ts`: the server-owned thread store (`load`, `claim`/`release` for the one active run, idempotent per-step `commit`, `runEnded`) and `layerMemory`. `load` returns each entry with the `runId` of the commit that appended it (`history` and `delta` rely on it). Compaction is the store's concern: the prompt is built from whatever `load` returns, but `delta` and `resume` read it too, so a compacted thread must keep the client's latest ids and any unanswered approval requests, and must not add a non-system entry after the latest one the client has seen (`HistoryDiverged`).
- `Checkpoint.ts`: memoises named steps of a run (`memo`), keyed by `(threadId, runId, name)`. `layerNone` (tests, evals), `layerLedger` over a caller-supplied `Ledger` (`layerMemoryLedger` for tests), `layerWorkflow` (activities; build it inside a workflow execution). Completed exits, including failures, are stored; interrupted attempts are not.
- `EventLog.ts`: a run's AG-UI events under increasing cursors, keyed by `(threadId, runId)`; `subscribe` checks the cursor first (an unissued one fails with `InvalidCursor` before any stream exists, so routes can answer 400), then yields history then live events and completes after the terminal event, at once if the cursor is already past it. `read` rejects unissued cursors too. `layerMemory`.
- `Runner.ts`: the AG-UI edge. All runners share one pipeline: build `Options.layer` from the dependencies the run was provided, in the attempt stream's scope (not memoised: every attempt and replay builds it again); check the input against the run's memoised `input` (`RunInputMismatch` if it differs; the dependencies aren't part of it), claim the thread (`ThreadBusy` if another run is active), load the thread, take the client's delta and `resume` answers, commit them, project the thread (memoised as `prompt`), run the agent with `RunInfo` (`props` from `forwardedProps`) and the per-run services provided, committing each `StepFinished`, call `runEnded` and then `release` (after the failure catch, so every non-interrupted run that claimed the thread reports its end, including pre-core failures, and before the terminal event is emitted), then `AgUi.fold`. `run` also releases a run whose stream stops before its terminal event (a cancelled request); detached and workflow runs keep the claim until they are resumed and end. Choose a runner by whether a disconnect should cancel the run:
  - `run` is request-scoped: the consumer stopping cancels the run. It's a plain function and captures nothing. A route calls it in its handler, provides the per-request service, and closes over the handler's context (`Effect.context` + `Stream.provideContext`) before handing the stream to the response, since the body is read after the handler has returned (the examples' `sse` helper). With `effect/http` the handler's services must be in the app layer's output (`Layer.provideMerge`), which `toWebHandler`/`serve` provide per request; `Layer.provide` hides them, and the web handler then demands a context argument.
  - `makeDetached` forks the run into a caller-owned scope and writes it to the `EventLog`; disconnects don't reach it. Starting the same input again completes a crashed attempt: nothing happens if the log is terminal, otherwise open spans are closed, `RUN_STARTED` isn't repeated, and replayed steps publish nothing.
  - `workflow` is the detached body as an `effect/workflow` workflow named by the required `WorkflowOptions.name` (unique per agent on an engine; it is persisted, so never default or rename it) and keyed by the input's thread id and run id, with `Checkpoint.layerWorkflow`. Its dependencies must be `RunContext`s; its payload schema is built per workflow from them (`{ input, context }` keyed by each one's key, or `{ input }` with none), so a resumed execution has its dependencies and the engine validates them on encode. `start(input)` reads the dependencies from the caller, builds the payload and executes with `discard`; `executionId(input)` needs them too, because the engine derives the id from the encoded payload.
  - `Options.layer` builds per-run services on every runner. `DetachedOptions.dependencies` (`makeDetached`, `workflow`) lists services each run requires from its caller (any service key, like a tool's `dependencies`; `RunContext`s for `workflow`), because those runners capture their services when built and must leave these out; `run` has no `dependencies`, since it captures nothing. `RunContext<Self>()(key, { schema })` is a `Context.Service` class plus its `schema` (not `context`, which clashes with `Context.Service`'s own method). Runners take only the input: `run` leaves every service on its stream, and `makeDetached`'s `start` leaves the dependencies (`DependencyServices<Dependencies>`), reading them before forking. `Requirements` (what a detached or workflow runner captures; a `run` stream requires it with no dependencies) is the agent's requirements minus what the layer provides and the dependencies, plus the layer's own needs, plus `Thread` and `Checkpoint` (used before the services exist). Read a dependency's service type from its key's `Identifier`, not `InstanceType`, which is `any` for these classes.
- `Sse.ts`: encodes AG-UI events as SSE frames, the format `@ag-ui/client`'s `HttpAgent` expects. `encodeStored` sets each frame's SSE `id` to the event's cursor, for `Last-Event-ID` reconnects. `response` is the `effect/http` response for those frames: it closes over the context it's built in (the body is read after the handler returns), and sets `text/event-stream` and `cache-control: no-cache`, with the caller's `headers` merged over them. It's the module's only `effect/http` import; the encoders stay transport-free.

## Resume rules

- **Approvals.** A tool with `needsApproval` ends the run with `RUN_FINISHED` outcome `interrupt` (one interrupt per approval, `reason: "tool-approval"`). The next run on the thread answers with `resume` entries; approved calls execute as step 0 before the model is called. A run that leaves an open approval unanswered fails with `UnansweredInterrupt` (AG-UI 1.0 forbids reading an omission as a decision); the client gives up on one by answering `cancelled`.
- **Run context.** A detached run doesn't store its dependencies: restarting one means calling `start` with the same input and the same dependencies provided, and builds the per-run services again. A computed system prompt is memoised as `system`, so a resumed run sends the first attempt's text even if the services it read changed.
- **Crashes.** Re-running a `runId` with a durable `Checkpoint` replays completed model and tool steps (same ids, no repeated handlers) and re-executes only the step that was in flight, with fresh ids. A step that _failed_ is memoised too: a failed run stays failed, and the client retries with a new `runId`.

## Invariants

- **One active run per thread.** Every runner claims the thread before loading it and releases it before the terminal event. Never load or commit outside a claim, and never emit `RUN_FINISHED`/`RUN_ERROR` for a claimed run before releasing it, or a client's immediate next run gets `ThreadBusy`.
- **Every key for a run includes the thread id.** The client picks `runId`, so checkpoints, the workflow idempotency key and the event log are keyed by `(threadId, runId)`. The caller authorises the thread, and that must be enough to authorise its runs.
- **Per-run dependencies never come from the AG-UI input.** Only the runner's caller provides them (the verified principal, not the token), and they reach the agent only as services; the client's `forwardedProps` only ever becomes `props`, which is untrusted. A per-run layer failure happens before the claim, so it isn't reported through `runEnded`.
- **The event streams never fail.** `Agent.run` reports errors (model failures, `StepLimitExceeded`, …) as one in-band `Failed` event, and the AG-UI streams as `RUN_ERROR`; the error type is `never`. Keep it that way.
- **Every emitted sequence must be valid AG-UI.** That means a run lifecycle (`RUN_STARTED` … `RUN_FINISHED`/`RUN_ERROR`), and text messages, tool calls and steps that are started, then ended, never left open. This includes an event log completed by a resumed attempt.
- **Side effects go through checkpoints.** Every model call, tool call and id minted in a run happens inside one `Checkpoint.memo`, so a replay is deterministic and handlers run at most once per run.
- New tools should normally use `failureMode: "return"`, so their failures go back to the model instead of ending the run.

## Tests

- Use `@effect/vitest` (`it.effect`) for anything effectful.
- `test/fixtures.ts` provides a `scriptedModel(steps)` fake `LanguageModel`. Each step is the stream for one `streamText` call, and it records the prompts it receives. It also provides part builders (`text`, `toolCall`, `finish`), a sample `WeatherToolkit` with `countingWeatherLayer()`, an `ApprovalToolkit` (adds `send-email`, which needs approval) with `countingApprovalLayer()`, `evalLayers` (`Checkpoint.layerNone` + `counterIds`), `runAgUi` (several inputs through `Runner.run`), deterministic ids (`counterIds`) and `verify`.
- To test a crash, stop consuming the run mid-step (or close a detached run's scope) and run the same `runId` again against a shared `Checkpoint.layerMemoryLedger`.
- **Pass every event sequence a test produces through `verify`.** It runs `@ag-ui/client`'s own sequence checks, so the tests catch streams a real client would reject.
- Don't call a real model in tests.
